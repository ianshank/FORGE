**Status:** partial — handshake + first-real-episode rollouts captured
end-to-end against a real `itzg/minecraft-server`. Full 100-episode
random capture blocked by an upstream mineflayer connection-stability

- **Hardware**: Windows 11 / Docker Desktop (WSL2 backend), x86_64
- **Minecraft**: `itzg/minecraft-server:latest` (1.20.4 default),
  6 GB RAM, MC_EULA=TRUE in `docker/compose.minecraft.env`
- **mc-bot**: v0.5 image built from `docker/mc-bot.Dockerfile`
  (1.28 GB), running mineflayer 4.x against Java MC 1.20.4
- **forge-mc-runner**: v0.5 image built from
  `docker/mc-runner.Dockerfile` (135 MB) with `--features mc-live`
  (random-baseline-only; trained-mode `mc-live-bundled` deferred —
  see "Known infrastructure issues" below)
- **Branch sha**: `1797d71` (PR #60 HEAD)


## Known infrastructure issues — surfaced during this run

### 1. Mineflayer bot connection becomes stale after first MC server-side error

Symptom: after the bot's mineflayer hits a server-side exception
(e.g. "ForgeBot tried to attack an invalid entity" — a random
`attack` action with no entity in melee range), the bot's
WebSocket layer stays UP but its mineflayer connection to the MC
server enters a half-open state. Every subsequent `step` request
returns `Timeout waiting for N ticks after ~5s` because the bot
no longer receives game ticks from MC.

**Mitigation**: the `mc-bot` container needs an auto-reconnect path
that detects MC-side timeouts and re-runs the `createBot` → spawn
sequence. Out of scope for v0.5 Phase 1 (orchestration/UX
hardening, not the block-grid contract); tracked as Phase 2.

**Workaround for now**: restart the bot container between runs:

```bash
docker compose -f docker/compose.minecraft.yml --env-file docker/compose.minecraft.env restart mc-bot
```

### 2. `--features mc-live-bundled` build pipeline

`ort 2.0.0-rc.12` has three cascading dep conflicts:

- `download-binaries` feature pulls `ureq 3.x` whose `tls` module is
  feature-gated → build script fails.
- `load-dynamic` + manual `libonnxruntime.so` install: the rc.12 ABI
  rejects the 1.22.0 shared lib (`unknown field
  CreateEnvWithCustomLoggerAndGlobalThreadPools`).
- Workspace `Cargo.lock` pins versions whose transitive deps
  (`fixed 1.31`, `icu_* 2.2`, `ort-sys 2.0.0-rc.12`) require
  rustc 1.93 — required a 1.82 → 1.88 → 1.93 toolchain bump.

The v0.5 Dockerfile builds the **`mc-live` (random-only)** variant
cleanly with rustc 1.93. The trained-mode variant
(`mc-live-bundled`) needs a separate infrastructure ticket to
either downgrade `ort` to a stable rc.9 line or forward-port
`forge-agent::onnx_model.rs` to whatever rc.12 ABI accepts.

Until then, trained-mode runs need the operator to bring their own
`ort`-compatible runner binary (or wait on the infrastructure
ticket). Random-baseline runs work today via:

```bash
# Stand-in for the runner image, drives random episodes via WS:
python scripts/v05_manual_baseline.py --episodes N --max-steps-per-episode M
```

## First-hour observations

- v0.5 handshake validated end-to-end against the real
  `itzg/minecraft-server` — **no plan-level mismatches surfaced**.
  Every field (`obs_dim`, `grid_shape`, `schema_id`, `action_count`)
  matched the plan's specification byte-for-byte.
- mc-bot per-connection INFO log fires cleanly:
  `[mc-bot] block-grid encoder enabled: h=11 w=11 d=1 ch=7
   vector_dim=73 total=920`.
- Episodes that DID run (4 across the three runs) produced sensible
  rewards — survival/inventory/distance/health composite signals
  varied between −7 and +40 over 11-400 random-action steps, which
  is the right order of magnitude for the existing reward weights.
- The bot's protocol-error path correctly emits `INTERNAL` codes
  with timeout messages; the v0.5 capture-baseline subcommand's
  truncate-and-continue logic (peer-review #5) gracefully handles
  this without corrupting the per-episode record schema.

## Anomalies + lessons learned

- Initial v0.5 stack-up surfaced FOUR docker integration issues
  the v0.4 PR-CI never caught (because v0.4 testing was all stubbed):
  - GHCR runner image was never actually published (was a placeholder
    string in compose); local builds via `docker/mc-runner.Dockerfile`
    are now the canonical path.
  - mc-bot's `DEFAULT_CONFIG_DIR` resolves to `/configs/minecraft`
    (relative to `/app/src`); the compose mount target had to be
    duplicated.
  - `env.toml::ws_url` was pinned at `ws://127.0.0.1:8765` (works
    for local dev, breaks docker compose networking); switched to
    `ws://mc-bot:8766`.
  - `env.toml::bot.host` was pinned at `127.0.0.1`; switched to
    docker service name `minecraft`.
- Bot host-port `8765` collision on the dev host required bumping
  to `8766` end-to-end (env file + env.toml). Fix is permanent but
  the rest of the system is fine with whatever port.
